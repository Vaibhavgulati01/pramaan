# Safety

PRAMAAN is defence-only by construction. Every claim below names the file
or command that lets you check it rather than asking you to take it on
trust.

## No generative model, anywhere

**Check `pyproject.toml`.** The dependency list contains no image
generator, no diffusion library, no GAN. The heaviest model in the tree
is CLIP ViT-B/32 (`open-clip-torch`), used only to *embed* images into a
vector for near-duplicate search — `src/pramaan/pillars/clip_embed.py`
calls `encode_image` and nothing else. There is no decoder, no sampler,
and no path from an embedding back to pixels.

We did not build a fake-damage generator even for evaluation, where it
would have been the convenient thing to do. Every synthetic image in
PRAMAAN-Bench-v1 is drawn from a pre-existing public academic benchmark
(GenImage, via a Hugging Face mirror) — see `benchmarks/sources.py` and
`docs/DATA_CARD.md`. Under a track that disqualifies offence-capable
work, the *absence* of a generation pipeline is a positive signal a
reader can verify by reading the dependency list.

## The API cannot be used as an evasion oracle

An attacker's most valuable tool is a system that tells them how close
they are. `src/pramaan/api/` (Phase 8) returns a tiered decision
(`APPROVE`/`REVIEW`/`DENY`) and templated reason codes only. It does not
return:

- raw fused probabilities or per-pillar scores,
- SHAP values or any gradient,
- distances, similarities, or match counts,
- the identity of a matched prior claim.

Reason codes are rendered through a deterministic template layer from
already-computed SHAP attributions (Phase 7), never generated by a
stochastic text model — both because an adverse-action decision must be
auditable, and because free-text generation leaks detail templates
cannot.

## Absent evidence is never adverse

Two pillars can return "I don't know", and in both cases that is the
*normal* result rather than a suspicious one:

- **Provenance (P1).** Practically no consumer photo in India carries
  C2PA — WhatsApp, the dominant channel for sending a merchant a damage
  photo, strips it. `src/pramaan/pillars/p1_provenance.py` encodes this
  as `UNKNOWN`, and every feature it emits is a *positive* assertion, so
  a missing manifest produces an all-zero vector rather than risk.
  Measured on the dev corpus: 400/400 real claims report `UNKNOWN`.
  Asserted by `test_unknown_contributes_nothing_in_either_direction`.
- **Forensics (P2).** A PNG has no quantisation tables; most messaging-app
  images have no EXIF thumbnail. Both are recorded as absent, never as
  evidence.

A system that read silence as guilt would deny essentially every honest
claim in this market.

## Robustness testing perturbs only our own inputs

The shift matrix (§6, Phase 6) recompresses, crops, strips metadata from,
and screenshot-round-trips **our own held-out images**, to measure **our
own** degradation and publish where our guarantee stops holding. No
third-party system is probed, and no perturbation is tuned to defeat any
detector other than ours. This is standard defensive evaluation.

## Auto-deny requires more than the image pillars

The abstention band exists precisely so that uncertain cases go to a
human rather than to an automated denial. The cost model
(`configs/costs.yaml`) prices a false positive *above* a false negative
at typical order values, so the policy is structurally biased against
denying an honest claimant.

## The federated index stores no personal data

`src/pramaan/federated/` (Phase 7) publishes salted perceptual-hash bands
(HMAC under a rotating consortium key) and differentially-private counts.
Never images, names, phone numbers, addresses, or any raw identifier.
Anti-poisoning rules — including first-seen immunity, which is already
implemented in `src/pramaan/pillars/rings.py` — are documented and
measured in `docs/THREAT_MODEL.md`.

## Dual-use assessment

The techniques here (perceptual hashing, CLIP embedding, JPEG forensics)
are all long-published and widely available; nothing in this repository
advances an attacker's capability. What the repository does add is on the
defensive side: a calibrated abstention policy, a certified bound on the
false-denial rate, and an honest account of when that certificate fails.

The one genuine dual-use consideration is that publishing *which*
signals we rely on tells an attacker what to avoid. We judge this the
right trade: the reuse graph — our strongest pillar — is hard to evade
without abandoning image reuse altogether, which is itself the win;
`docs/LIMITATIONS.md` states plainly where we are weak; and a fraud
system whose defensibility depends on nobody knowing how it works is not
one anyone should deploy against real claimants.

Full analysis, including attacks against PRAMAAN itself:
[`docs/THREAT_MODEL.md`](docs/THREAT_MODEL.md).
